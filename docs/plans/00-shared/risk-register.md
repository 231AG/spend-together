# Risk register

Likelihood and impact are Low / Medium / High. "Owner phase" is the phase that carries
the mitigation. Reviewed at every phase approval gate.

| # | Risk | L | I | Mitigation | Owner phase |
|---|---|:-:|:-:|---|---|
| R-01 | **Major-version stack churn.** Next 16, TypeScript 7, Vitest 5, ESLint 10 and Lucide 1.x are all newer majors than the spec was written against; peer-dependency conflicts or breaking API changes could stall F0. | H | M | F0's first ticket is a compatibility spike that installs the full set and runs a hello-world through lint, typecheck, build and test **before** any product code. Pin exact versions, no caret ranges. If a conflict is unresolvable, drop to the previous major of the offending package and record it in `tooling-and-skills.md`. | F0 |
| R-02 | **Contract drift between MSW and the real API.** The frontend is finished months before the backend; divergence turns B8 into a rewrite. | M | H | ADR-002: one fixture directory consumed by both MSW handlers and backend contract tests. B5's contract tests are the same assertions the mocks satisfy. Any schema change after F1 needs an ADR. B8 runs the full Playwright suite against the real stack before mocks are retired. | F1, F4, B5, B8 |
| R-03 | **Money rounding bugs.** Half-away-from-zero, per-record rounding, exponent differences (JPY 0, KWD 3) and pace rounding order (ADR-004) are all easy to get subtly wrong, and errors compound through aggregates. | M | H | All arithmetic confined to `packages/domain` with a 100% line+branch gate; branded `MoneyMinor` type makes accidental float math a type error; ESLint bans `parseFloat` on money; T-11, T-12 and the §6.5 worked example are asserted verbatim. | F2 |
| R-04 | **A privacy regression leaks partner data.** The product's core promise (BR-05) and its main reputational risk. | L | H | Enforced twice (application guard + RLS). pgTAP asserts owner / partner / stranger / ex-partner for every table (§23.2). MSW mocks enforce BR-05 too, so a frontend built against mocks cannot even *render* a leak. 404-not-403 everywhere. A dedicated E2E couple scenario with two real sessions. | B2, B8, F4 |
| R-05 | **Timezone and period-boundary errors.** ISO weeks, IANA day boundaries, month edges, and the current-vs-completed-period rule in F-07. | M | M | `date-fns-tz`, injected clock, no ambient `Date`. T-13 (Monrovia vs Tokyo at 23:30 on 31 Aug), T-14 (ISO Monday weeks) and T-15 (day-17 divisor) are mandated tests. Insights E2E covers a month boundary. | F2 |
| R-06 | **Offline outbox complexity.** Queue, retry, backoff, idempotency, permanently-rejected items, and the logout-with-pending warning are a lot of state for a SHOULD requirement. | M | M | Idempotency keys make retries safe by construction; client-generated UUIDs are the record ids; max 8 attempts then the item moves to "Needs attention" with a reason and Edit/Discard — data is never silently dropped. If schedule pressure arrives, Q7 in open-questions is the documented cut. | F12 |
| R-07 | **FX provider unreliability or missing currencies.** Free-tier provider may omit LRD or go down; stale rates silently distort every total. | M | M | Primary + automatic fallback behind an `FxProvider` interface swappable via `app_config`. Pre-build availability check sets `is_active = false` for any currency without a rate. Retries at 01:30 and 03:00. 72-hour staleness alerts to Sentry; users see "Rates last updated …". `fx_estimated` flag surfaces in the UI. | B6 |
| R-08 | **Base-currency recalculation is slow or partial.** Rewriting every `base_amount_minor` in one transaction has a stated < 5 s target for 10,000 records. | L | M | Runs in one transaction so it cannot half-apply; `recalculating: true` in API responses with a UI banner over prior values; load-tested at 10k and 100k records in B6; rates read from the stored daily table, not the network. | B6 |
| R-09 | **The 100% domain coverage gate becomes a merge blocker.** A strict gate on a large surface can stall unrelated work. | M | L | The gate applies to `packages/domain` only, and that package is written *once* in F2 with its tests, not incrementally. Later phases import it rather than extend it. Any new domain function arrives with its test in the same commit. | F2 |
| R-10 | **Accessibility discovered late.** Retrofitting WCAG 2.2 AA after 22 screens exist is a project in itself. | M | H | Radix primitives from F3; axe runs per component state in Storybook from F3 onward, not just in F13; every UI ticket's acceptance check includes the keyboard and focus path; serious/critical violations fail CI from F3. F13 is a verification pass, not a remediation pass. | F3, F13 |
| R-11 | **Seed data guessed wrong** (currencies Q4, categories Q5). Fixtures, tests and screenshots all bake in the guess. | M | M | Both are isolated to `supabase/seed.sql` and one fixtures module, and both are flagged Assumed in open-questions. Changing them is a data edit plus a fixture regeneration, not a code change — provided nothing hard-codes a category id. Enforced by a lint rule banning literal category UUIDs outside fixtures. | B1, F4 |
| R-12 | **Estimates are optimistic on the two deep phases.** F3 (design system, 23 components × full state matrix) and F13 (hardening across 22 screens × 5 breakpoints × 4 states) have the widest error bars. | M | M | Both are flagged as high-uncertainty in `README.md`. F3 is split so primitives land before feature widgets, giving an early signal. F13's scope is fixed by a checklist, so overrun is visible in tickets remaining rather than discovered at the end. | F3, F13 |
| R-13 | **Supabase local stack needs Docker.** If the dev or CI environment cannot run Docker, every backend phase from B1 is blocked. | L | H | Verified as B0's first ticket, before any migration is written. CI uses `supabase start` in a job with Docker available. If unavailable, fall back to a hosted staging project for tests, at the cost of slower feedback — recorded as an ADR if it happens. | B0 |
| R-14 | **Third-party account lead time** — fxfeed.io key, Twilio account and number, Resend domain with SPF/DKIM/DMARC. Procurement and DNS propagation are not engineering time. | M | M | Raised now as Q12 in open-questions rather than at the start of B4. B4 and B6 can be built against mocked providers and switched at integration, so lead time overlaps development instead of blocking it. | B4, B6 |
| R-15 | **Scope creep through "obvious" additions** — dark mode, recurring transactions, goal withdrawals all feel small and are all explicitly excluded. | M | M | §26 is quoted in `CLAUDE.md` and in `conventions.md`. Every ticket names the FR it serves; a ticket that cannot name one is out of scope by construction. Ideas go to open-questions. | All |
